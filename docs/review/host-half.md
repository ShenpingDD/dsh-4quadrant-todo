# Host 半缺陷识别与下一版本设计方案

范围：`lib/index.js`（Host 半，596 行）、数据文件读写、版本与结构校验、9 条 Remote 路由、父子联动与来源去重的服务端规则。本文只给方案，本轮未修改插件代码；新增的两个脚本是取证工具，位于 `tests/host-rules/`。

## 1. 结论

1. 已安装版本按 PRD 第 7、8、12 节实现了主要规则。39 条可判定的服务端规则中 34 条通过，父子联动的全部 10 条主路径与版本校验的主路径可用；安装副本与仓库文件 SHA-256 完全相同（`FEA01C7637970C7AC2869EE6549D330EE95F9344EBBDB0B78E2832910332715D`），实测对象就是生效中的代码。
2. 下一版本需要修 6 项缺陷：并发首次读取的竞态、来源去重可被 `/create` 绕过、加载校验缺 `collapsed` 取值类型、缺 `dueAt` 与 `completedAt` 类型、缺 `id` 唯一性、缺 `parentId` 悬空检查。前两项会造成用户可见的错误页与重复卡片，后四项会在文件被外部改坏时静默加载出错误数据。
3. 4 项需要产品裁定：合并完成是否覆盖已完成子待办的完成时间、撤销父任务后新增子待办是否再次自动完成、已完成的来源条目是否仍算「已存在」、删除后再次加入是否新建。当前行为已测出具体取值，见第 4 节。
4. 2 项文档与实现不一致：PRD 第 14.2 节的方法面与依赖声明，PRD 第 13 节性能目标与第 12.4 节规模上限在 1 万条已完成记录处互相冲突（实测读取 423 毫秒、写入 625 毫秒）。
5. 用户提出的四个问题里，没有一个的成因位于 Host 半。角标计数的取值规则在客户端按「未完成且无父待办」过滤（`lib/client.js:348`），与 PRD 第 5.1 节一致；Host 只需继续返回全量 `todos` 与 `collapsed`，本轮的四个问题不需要 Host 改动。

## 3. 缺陷清单

每条给出位置、触发条件、影响、最小修法、回归用例。回归用例号与 `verify-host-rules.mjs` 中的编号一致。

### D1 并发首次读取的初始化写入没有进入写队列

- 位置：`lib/index.js:240-243`（`readData` 的 `ENOENT` 分支直接调用 `writeData`）、`lib/index.js:174`（临时文件名固定为 `todos.json.tmp`）、`lib/index.js:521-524`（`snapshot` 不经过 `enqueue`）、`lib/index.js:288`（只有写请求进入 `enqueue`）。
- 触发：数据文件不存在时同时到达两个及以上读请求，或一个读请求与一个写请求同时初始化。
- 影响：实测 5 轮、每轮 8 个并发读，40 次里 30 次与 32 次（两次独立复跑）返回 500「数据文件不可写…ENOENT: rename …todos.json.tmp」。两个请求共用同一个临时文件，先完成的请求重命名成功后，后完成的重命名找不到临时文件。面板会显示错误页；PRD 第 12.2 节写明界面不做重试，用户需要关闭面板再打开。文件本身在 40 次里 0 次不可解析，重开即可恢复。真实界面里 `loadSnapshot` 有 `store.loading` 互斥（`lib/client.js:90-106`、`lib/client.js:343-345`、`lib/client.js:391-393`），单个窗口一次只发起一个读请求，因此这是潜在风险而非当前界面的必现问题；两个窗口、两次刷新或面板与侧栏在不同提交中分别挂载时可以触发。
- 最小修法：把「文件不存在则建立空结构」的写入放进同一条写队列（`enqueue`），临时文件名改为每次写入独立（带随机后缀），写入失败时删除该临时文件。
- 回归用例：C13（40 次并发读全部 200）、C11（首次读取建立空结构）、C14（10 个并发写全部成功且写入 10 条）。

### D2 来源去重只在 `/fromConversation` 内检查，`/create` 可以写入同 `sourceKey` 的第二条

- 位置：`lib/index.js:303` 与 `lib/index.js:316`（`create` 接受并保存请求里的 `source`，同时计算 `sourceKey`）、`lib/index.js:495`（去重判定只存在于 `addFromConversation`）。
- 触发：任何带 `source.kind === 'conversation'` 的 `/create` 请求，或数据文件被手工编辑出同 `sourceKey` 的重复条目。
- 影响：实测同 `sourceKey` 的顶层条目变成 2 条（B9）。此后 PRD 第 10.4 节的去重只命中第一条，「已存在」提示把用户带到其中一条，另一条成为重复卡片；两条的完成状态各自独立。
- 最小修法：`sourceKey` 的唯一性作为写前不变量。`create` 遇到会话来源时走与 `addFromConversation` 相同的判定（已存在则返回既有标识并标记 `existing`），或在写前扫描同 `sourceKey` 顶层条目并拒绝。
- 回归用例：B9（数据文件中同 `sourceKey` 只有 1 条）、B1（重复加入不新增）。

### D3 加载校验未检查 `collapsed` 的象限取值类型

- 位置：`lib/index.js:216-220`（只检查每个工作区条目是对象）。
- 触发：数据文件里 `collapsed.<scope>.<quadrant>` 不是布尔值。
- 影响：实测 `collapsed.all["urgent-important"] = "yes"` 时 `snapshot` 返回 200（C7），客户端按真值处理，该方格保持折叠且不受折叠按钮控制。PRD 第 12.1 节规定值为布尔映射，第 12.2 节要求每次读取做结构校验。
- 最小修法：校验每个工作区条目的键属于四个象限标识，值为布尔；不通过时抛出与现有格式一致的错误文本。
- 回归用例：C7（返回 500）、C6（非对象时返回 500，现有行为）。

### D4 加载校验未检查 `dueAt` 与 `completedAt` 的类型

- 位置：`lib/index.js:196-206`（`assertTodo` 覆盖了 `id`、`title`、`description`、`quadrant`、`status`、`parentId`、`createdAt`，未覆盖 `dueAt`、`completedAt`、`workspaceId`、`source`、`sourceKey`）。
- 触发：数据文件里 `dueAt` 是数字或任意字符串，`completedAt` 不是 `null` 或字符串，`source` 不是对象。
- 影响：实测 `dueAt: 123` 时 `snapshot` 返回 200（C8）。客户端 `dueTime` 对它返回 `null`（`lib/client.js:151-155`），该条被当成无截止时间参与排序且不显示逾期，用户看到错误顺序与缺失的时间；`formatMoment` 对数字会显示 1970 年的时间。整个过程不报错。
- 最小修法：`dueAt` 为 `null` 或匹配 `DUE_AT_PATTERN` 且可解析；`completedAt` 为 `null` 或同规则；`workspaceId` 为 `null` 或字符串；`source` 依次校验 `kind` 与三个必填字段；`sourceKey` 为 `null` 或字符串且与会话来源的三段拼接一致。
- 回归用例：C8（返回 500）、C19（写入侧的类型校验，现有行为）。

### D5 加载校验未检查 `id` 唯一性

- 位置：`lib/index.js:199`。
- 触发：数据文件出现两条相同 `id` 的待办。
- 影响：实测返回 200（C9）。客户端 `applyDelta` 按 `id` 建映射（`lib/client.js:82-88`），后一条覆盖前一条；React 列表键冲突；完成与删除只作用于第一条，另一条静默丢失。PRD 第 7 节把 `id` 定义为唯一标识。
- 最小修法：载入时用集合校验唯一性，重复即拒绝加载。
- 回归用例：C9（返回 500）。

### D6 加载校验未检查 `parentId` 是否悬空或指向子待办

- 位置：`lib/index.js:204`（只检查类型为 `null` 或字符串）。
- 触发：数据文件里 `parentId` 指向不存在的标识，或指向另一条子待办形成两层。
- 影响：实测悬空 `parentId` 时返回 200（C10）。客户端按父任务分组渲染子待办，孤儿子待办不会出现在任何方格；已完成清单只列顶层待办，也不会收录它。该条永久不可见却占用文件。PRD 第 7 节规定 `parentId` 有值时必须指向存在的顶层待办。
- 最小修法：载入时建立 `id` 集合，`parentId` 为 `null` 或命中集合且目标条目的 `parentId` 为 `null`。
- 回归用例：C10（返回 500）、A9（写入侧拒绝第二层，现有行为）。

### D7 写入失败后残留临时文件

- 位置：`lib/index.js:226-232`（失败路径不清理 `todos.json.tmp`）。
- 触发：磁盘已满、权限不足、目录被占用。
- 影响：`todos.json.tmp` 留在数据目录。实测残留的半截临时文件不影响正式文件读取（C12），因此影响限于目录里多出一个文件与后续排错时的困惑。
- 最小修法：与 D1 的独立临时文件名一并处理，失败时删除本次的临时文件。
- 回归用例：C12（读取不受影响）、C21（写入失败返回 500 且错误含路径，现有行为）。

## 6. 规模与性能实测

按 PRD 第 12.4 节的上限造真实数据文件，取 5 次的中位耗时。

| 数据量 | 文件大小 | `GET /snapshot` | `POST /create` | `POST /update` |
| --- | --- | --- | --- | --- |
| 1000 未完成 + 0 已完成 | 0.55 MiB | 39 ms | 37 ms | 53 ms |
| 1000 未完成 + 2000 已完成 | 1.68 MiB | 156 ms | 217 ms | 195 ms |
| 1000 未完成 + 10000 已完成 | 6.23 MiB | 423 ms | 383 ms | 625 ms |

PRD 第 13 节要求「打开面板到内容可见在 300 毫秒内」，第 12.2 节要求每次写操作整文件写入。这两条在 1 万条已完成记录处无法同时成立：读取 423 毫秒，单次写入 625 毫秒，而界面每次勾选都会触发一次整文件写入。

下一版本的处置建议：把 PRD 第 12.4 节的已完成记录上限从 1 万条改为 2000 条，实测在该量级读取 156 毫秒、写入 195 毫秒，仍在 300 毫秒目标内，同时不改动第 12.1 节的文件结构与第 12.3 节「不做自动迁移」的限制。单人本机使用在一年内很难产生 2000 条以上已完成记录；达到上限时按第 12.5 节手工导出或另存。
